# Architecture

```
 GitHub     ┌─────────── web/ (single source of UI, no build, no runtime deps) ───────────┐
 Pages ───► │ index.html + CSP('self')   sw.js (offline)   manifest                        │
            │ js/app.js  router ─► ui/*.js   (DOM via h(), text nodes only)                │
            │ util.js, i18n.js (he/en, RTL)                                                │
            │ native.js ── no-op in browsers ───────────────────────────────┐              │
            └───────────────────────────────────────────────────────────────┼──────────────┘
                                                                            ▼ window.StepUpNative
 APK (GitHub Releases, always latest)   android/  MainActivity (WebView on https://appassets.androidplatform.net, assets = ../web)
                                         NativeBridge (the only door from JS into Android; validates every argument)
```

* **One codebase for UI.** The APK has no UI code of its own; Gradle packages `web/` as assets. Native code adds only what browsers cannot do (background work, system integration).
* **Dependency direction.** `ui/* → store/engine/stats/share → util/config`. Logic modules stay **pure** (no DOM, no storage, time passed in as `now`). Web code reaches Android only through `js/native.js`; Android code is reached only through `NativeBridge.kt`. Logic that must also run natively lives in `*Math.kt`-style objects without Android types, with JVM tests.
* **No server.** Data lives on the device (IndexedDB when persistence is added; always with a memory fallback when storage is blocked).
* **Versioning.** `web/version.json` → PWA, service-worker cache name, APK `versionName/Code` (`npm run bump`).
* **Trust boundaries.** (1) Imported/shared/restored data → sanitise + normalise on load. (2) Web → Android → `NativeBridge` argument validation and size caps. (3) CSP `'self'` only + escaped DOM building (`h()`; `innerHTML` & co. are banned by `scripts/static-checks.mjs`).
* **Network.** Three uses, all explicit: (0) optional OpenStreetMap map tiles (images, `img-src`) when the person turns the street map on; (1) the weather forecast for recommendations (opt-in), (2) the "Check for updates" button (`update.js`: one GET to api.github.com public release list, CSP `connect-src` has it too; nothing about the person is sent). Weather details: see section "Network (0.4)" below ( `INTERNET` + CSP `connect-src` for api.open-meteo.com only). (3) the **route planner** (0.18.0, `planApi.js`, opt-in pref `planNet`, revocable in the planner): on a tap it sends the typed address to OpenStreetMap Nominatim, points along candidate routes to the FOSSGIS OSRM walking service, sampled points to Open-Meteo's elevation endpoint and the route outline to Overpass; CSP `connect-src` lists exactly those four hosts (plus the two above), every request is bounded (time, size), `credentials:'omit'`, `referrerPolicy:'no-referrer'`, answers are parsed by the pure `routePlan.js` parsers (untrusted JSON -> safe numbers) and any failed enrichment is shown as missing, never as good. Any other network use needs a written reason here.

**Route planner design (0.18.0).** `routePlan.js` (pure): `viaSets` builds candidates (loop = a ring through two via-points started in six directions + out-and-back; A to B = direct, or detours to both sides at three places when the target is longer than the direct way), `scaleVia` corrects the first guess about street winding after the first answers, `elevationStats` (3 m hysteresis), `classifyRoute` (nearest OSM way within 20 m per sample -> sidewalk / path / trail / road / unknown) and `countCrossings`, `scoreRoute` (distance 50% + climb, crossings, surface weighted by the person's preferences; missing data is neutral) and `rankRoutes` (drops near-duplicates). `planner.js` runs it against an injectable `api` so it is unit-tested without a network. The map screen (`ui/mapScreen.js`) reuses `mapView.js` (`fromXY` is the inverse projection) and the tile layer; without the street-map option it draws a plain grid and loads nothing.
* **Permissions.** `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`: workout distance from GPS, read only while a workout is on screen. The WebView's geolocation prompt is answered in `MainActivity` for our own origin only, after Android's runtime permission. The motion sensor (rhythm coach) needs no permission.

## Android background (0.6)
Web side: `native.js` (wrappers, no-ops in a browser), `ui/workout.js` (one `feed(fix)` door for page GPS and drained service fixes), `schedule.js` (pure: reminders for 7 days, recommendation entries, bounded 60), `syncNative.js` (collects and calls `native.setNotifications`, debounced, on start/hide/changes), `app.js#onFront` (pending href, step sample), settings block `backgroundBlock`.
Android side (`com.stepup.app`): `NativeBridge` (validated door) -> `TrackingService` + `Tracking` + `FixBuffer` (pure) · `StepStore` + `StepMath` (pure) + `StepReceiver` · `NotifyStore` + `NotifyMath` (pure) + `NotifyReceiver` + `BootReceiver` · `MainActivity` (runtime permissions via `ask`, tapped-notification route via `takeHref`).
Data flow of a workout: start -> `trackStart(title, text)` (asks for the location permission, returns false until granted; the page retries each tick) -> service appends `lat,lon,t,acc` lines to `files/fixes.txt` (bounded 2 MB, 20 000 lines) -> `trackDrain()` returns and clears them -> `addFix`. Privacy: nothing leaves the phone; the notification texts and the service text come from the page's current language.
Permissions and why: `FOREGROUND_SERVICE_HEALTH` (the all-day steps service, needs the steps permission) · `FOREGROUND_SERVICE(_LOCATION)` + location (screen-off tracking, user-started, visible notification) · `POST_NOTIFICATIONS` (reminders, recommendations, the tracking notification) · `ACTIVITY_RECOGNITION` (step counter, opt-in in Settings) · `RECEIVE_BOOT_COMPLETED` (re-arm alarms). Alarms are inexact on purpose (no `SCHEDULE_EXACT_ALARM`).

## Training plans (0.8)
`plan.js` is pure: `generatePlan` (effort curve from the baseline, growth rate by age, recovery every 4th week, taper, session types per week, days from habit or default spread, interval structure by level and week, long-session goal ramp), `matchSessions` (kind and >= 70 % of the planned minutes on the planned day; a workout is used once), `catchUpOptions` (move within 3 days or skip; <= 2 moves), `adaptAfterMisses` (-15 % next week, once per week), `planProgress`, `sanitizePlan`. Storage is one JSON in localStorage. `ui/plan.js` draws the builder and the week view (`mountPlan` is shared with the dashboard drill-down; the newest draw wins), `matchAfterWorkout` is called after a workout is saved. Reminders: `schedule.planEntries` -> `syncNative` (Android) and `reminderLoop` (browser).

## Home-screen widgets (0.7)
Three `AppWidgetProvider`s (`StepsWidget`, `EffortWidget`, `QuickWidget`) share `Widgets.updateAll`. Data: steps today come live from `StepStore` (sensor); goals, weekly effort and the translated texts come from the page's snapshot (`native.setWidgetData`, validated by `WidgetMath.parse`, stored in prefs `widgets`). Updates: a new step reading, a new snapshot, and the system's 30-minute cycle (`updatePeriodMillis`). A tap sends `MainActivity` an `href` extra (`#/d/steps`, `#/d/effort`, `#/workout/<kind>/go`), the same route channel as notifications. RemoteViews only (TextView + ProgressBar); no custom drawing, no network, no extra permission.

## Routes (0.5)
`route.js` (pure): `simplify` (Douglas-Peucker, <= 150 points), `makeRoute`, `matchRoute` (same direction; length within 20 %; start within 150 m, end within 250 m; 40 points sampled along each path must stay within 35 m on average and 120 m at most, in both directions), `distanceAtTime` (the ghost), `sanitizeRoute`. `routeReco.js` (pure): `attemptsOf`, `speedIndexes` (route median pace / attempt pace), `routeProgress`, `bestContext` (hour band and weather bucket with the best median index, needs >= 2 attempts), `recommendRoutes` (one-time routes skipped). Storage: IndexedDB v2 store `routes` (key `id`, <= 100) via `store.js`; a workout links with `routeId`. `ui/routes.js` (list, detail, quick actions, `summaryBox` after a workout), `ui/livemap.js` (tile-less map). Following a route: `#/workout/<kind>/go/r/<routeId>` (`go` = start at once).
Map tiles (0.14, decision D2 = opt-in): off by default; when on, `ui/maptiles.js` shows OpenStreetMap tiles (`mapView.js` computes the Mercator view and the tile list) under the path; without it the pictures are drawn from the recorded points only. CSP `img-src` allows `https://tile.openstreetmap.org`.

## Workout screen (0.15)
One screen, three phases: ready (GPS card, map, Start), running/paused (distance, pace-or-speed, time, map, Metronome/Voice/Sunlight, Pause + Finish), done (summary). Cues, the stop hint and records share one banner area above the map. Voice: the page speaks while visible; `Voice.kt` + `SplitTracker.kt` speak from the service while the screen is off (`Voice.foreground` is set by MainActivity.onResume/onPause); the page tells the service its baseline (`setVoice`: on, language, template, distance, moving time) whenever tracking starts or the switch changes.

## Battery (0.14)
GPS: 1 s fixes, 4 s after 15 slow fixes in a row (`TrackingMath`); service stops after 6 h. Widgets: each provider redraws only itself (the steps widget every 30 minutes, the others hourly). All-day steps: `StepService` (foreground, type `health`, minimised notification) keeps ONE `TYPE_STEP_COUNTER` listener with a 10-minute hardware batching latency and folds the newest value into the day through `StepStore.record` at most once a minute - this is the only dependable way, because Android 9+ delivers no step-counter events to a background app (so an alarm or a widget update cannot read it). Started by `StepStore.ensureService` from the app in front (`onResume`, `stepsSample`), the switch (`stepsKeep`) and `BootReceiver` (boot / update); stopped when the switch is off or the permission is gone. Fallback when the service is off: one inexact non-waking alarm every 15 minutes (fires as soon as the phone wakes), a reading when the app is left (`onPause`), at boot / after an update (`BootReceiver`) and whenever the steps widget is redrawn (`StepsWidget.onReceive` with `goAsync`, so the reading can finish); the reading registers with no batching delay and asks the sensor to `flush`. Notifications: one `setAndAllowWhileIdle` alarm for the next one. Page: reminder checks and workout painting skip while `document.hidden`. No wake locks outside a workout, no polling, no foreground service unless a workout runs.

## Permissions, defaults and the in-app update (0.24.0)
* **Permissions.** `permissions.js` lists what the app asks for (location, notifications, steps and the optional battery row on Android; location + notifications in a browser) and reads the state: Android through `NativeBridge.permissionState()` (`granted | ask | blocked | unsupported`; `blocked` = asked before and Android will not show its dialog again, decided by `PermMath`), a browser through the Permissions API / `Notification.permission`. `requestPermission(id)` asks (Android: the system dialog, or the phone's settings screen when blocked; the answer comes back as a `permissions-changed` event, also sent when the app returns from a settings screen). `ui/permissions.js` draws the Settings section and the start-up sheet (once per session, only when something required is missing, never over a workout, "Do not ask again" = pref `permAsk`).
* **Defaults** (owner's decision, replacing the old opt-in): the street map (`mapTiles`), the weather (`onlineWx`) and the route planner's services (`planNet`) are ON unless the person turned them off (one list, `ON_BY_DEFAULT` + `flag()` in `store.js`, so a toggle and its feature never disagree; `permAsk` is on the same list). The position (rounded, `weatherApi.ensureLocation`) is refreshed by itself at start and when a permission changes, but only once the location permission is granted - nothing prompts by itself. The sheet and the Settings text say that these use online services.
* **In-app update (Android).** The page may only pass an address `UpdateMath.validUrl` accepts (this project's release asset `stepup.apk`). `Updater` downloads it (HTTPS, 80 MB cap, timeouts), compares its SHA-256 with the published `stepup.apk.sha256`, checks the package name, a higher version code and the same signing certificates, then installs it with `PackageInstaller` (MODE_FULL_INSTALL, no uninstall, data stays); the result arrives at `InstallReceiver` (a PendingIntent of ours). Needs `REQUEST_INSTALL_PACKAGES` and Android's per-app "install unknown apps" switch (the page sends the person there once, then carries on by itself). Trust model: Android itself refuses an APK signed with a different key; the repository's signing key is committed on purpose (see RELEASING.md), so this protects against corruption and mix-ups, not against someone who has that key.

## Network (0.4) - the only internet use in the app
`weatherApi.js` makes ONE kind of request: `GET https://api.open-meteo.com/v1/forecast?latitude=..&longitude=..&hourly=..` (hourly temperature, apparent temperature, rain probability and amount, wind, UV, is_day, weather_code). Why: recommendations by weather (owner's request). Safeguards: opt-in (`onlineWx`, off by default, consent card + Settings), coordinates rounded to 2 decimals, nothing else sent, `credentials: 'omit'`, `referrerPolicy: 'no-referrer'`, 8 s timeout, 200 KB cap, 1 h cache (`da.wxc`), response normalised in `forecast.js` (finite clamped numbers only, at most 72 hours), CSP `connect-src 'self' https://api.open-meteo.com`, Android `INTERNET` (no cleartext, WebView still loads only our own origin). "Forget my location" clears the opt-in, the location, the cache and the notification setting. The service worker never touches cross-origin requests. Open-Meteo data is CC BY 4.0 and free for non-commercial use: keep the attribution and the request volume low (cache).

## Recommendations (0.4)
`reco.js` is pure: `comfort(hour, kind)` -> score + reasons/problems; `routineProfile(rows, now)` -> habit(weekday, hour) 0..1, sessions per day, typical minutes (needs >= 5 workouts, else the weather decides alone); `recommend(forecast, profile, kind, now, {tomorrow})` -> hours + items (habit / best / avoid, neighbouring bests merged); `generalRecs(ctx)` -> effort/steps/routine recommendations as i18n keys. `ui/reco.js` holds the consent card, screen, `mountReco` (shared with the dashboard drill-down) and the widget summary (saved forecast only: the dashboard never uses the network). `reminderLoop.js#recoPart` sends the optional notification (<= 45 min before a habit window with score >= 60, once per slot per day).

- **Dashboard:** `ui/dashboard.js` holds the widget table `W` (`summary` for the grid, `detail` for the drill-down), the saved layout/filter (validated against known ids), and a draw-sequence guard so only the newest async draw paints. ### Auto start of a workout (0.27.0)
`workout.js` (pure): `newWorkout(kind, now, { waitForMotion })` creates a workout with `waiting: true`; while waiting `addFix` only keeps the last ~25 s of accurate fixes (`warm`) and asks `detectStart(fixes, kind)` - the EARLIEST index from which the distance to the newest fix is >= `START[kind].minDistM` at >= `minSpeedMps` over 4-20 s and `d >= 0.6 x path` (a straight-ish stretch, not GPS wander; fixes worse than 25 m never count). On detection `startNow(w, firstFix.t)` back-dates `startedAt`, zeroes `pausedMs` and the window's fixes are replayed through the normal path. `elapsedMs` is 0 while waiting. `ui/workout.js` shows the `.waitstart` banner (status + "Start measuring now"), starts at once when GPS is denied/missing, and announces "Measuring started" (vibration if cues vibrate). Pref `autoStart` (default on; Settings). Saved workouts: `waiting` persists (a record without it was measuring). Both the page's watch and the Android service's drained fixes go through `feed -> addFix`, so detection works with the screen off.

### Weather screen (0.27.0)
`ui/weather.js` (`#/weather`): `groupDays` (local days, max 3) and `startHour` are pure; the place is `me` (the saved position, `fetchForecast`), a saved route (its first point) or a searched place (`planApi.geocode`, behind the planner's consent), stored in pref `wxPlace` (validated on read). `weatherApi.fetchPlace/cachedPlace` keep a separate cache `da.wxp` (4 places, 1 h each, rounded coordinates only; cleared by "forget my location"). The forecast hours carry `hum` (relative humidity, -1 = unknown). Charts: `charts.js` bars/line; the screen is reached from the sky row (`skynow.js`, now a link), search and the actions list.

### Chart animation (0.27.0)
Pure CSS in `app.css`: bars `scaleY` from the baseline with a per-bar `--i` delay, the line draws itself (`pathLength=1`, dash offset), dots and the target line fade in, `.meter > span` fills. `html[data-calm="1"]` and `prefers-reduced-motion` switch all of it off; the journey runs with reduced motion so screenshots are steady.

### Animated weather pictures (0.26.0)
The illustrator's 15 weather animations (12 frames each, flat magenta background) are cut by `scripts/make-weather-sprites.py` into `web/art/weather-anim/<condition>.webp` (a strip of 12 frames of 96 px, 452 KB for all 15, all precached) and `weatherAnimData.js`. The forecast request now also asks Open-Meteo for the hourly `weather_code` (same host, nothing else sent; stored as an integer 0-99, `-1` = unknown, also in the 1 h cache). `weatherAnim.conditionOf(code, day)` maps WMO codes to a condition (night pictures exist only for clear, mostly clear and partly cloudy; every other condition uses its day picture at night); `weatherIcon` draws the strip with `steps(12)` only while `.anim-on` (the calm switch and reduced motion stop it). `ui/skynow.js` shows picture + temperature + a word from the CACHED forecast (`skyNow`) or fills itself after the one hourly request (`skySlot`): on the Home day card and the Recommendations banner (the kit's static banner stays as the fallback).

### Sharing and what is new (0.25.0)
`ui/shareApp.js` builds the one share text (`shareText`: both links) and offers `wa.me` and `mailto:` links from `appShare.js` (pure, capped at 600 characters, percent-encoded), the system share (`native.share` / `navigator.share`) and the clipboard; no network call, nothing about the person. `ui/whatsnew.js` shows `changelog.js` (he + en) once per version (`da.seenVersion`; a first install only records it; skipped over a workout or while the permissions sheet is open) and from About. Adding a release = add its entry to `changelog.js` AND `docs/CHANGELOG.md` (a unit test enforces both).

### Service worker updates (0.24.1)
`sw.js` installs with `new Request(url, { cache: 'reload' })` so a new worker never stores files from the browser's HTTP cache (Pages: 10 min). `app.js` reloads once on `controllerchange` when a worker already controlled the page and no workout is in progress (`da.swReload` guards a loop).
